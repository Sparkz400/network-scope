# Supply chain: SBOM, provenance, signing and reproducible builds

Three checks let you confirm that a release file is what the project says it is and what is inside it. None of them replaces reading the source; they make tampering with a release visible.

| Check | Answers | Release file |
| --- | --- | --- |
| Signed SLSA build provenance (Sigstore) | Which workflow, repository and commit built this file? | `network-scope-<version>.sigstore.json`, `network-scope-<version>.intoto.jsonl` |
| SBOM (CycloneDX) | Which crates, at which versions, went into it? | `network-scope-<version>.cdx.json`, attestation `network-scope-<version>.sbom.sigstore.json` |
| Rebuild and compare | Does the source at this tag produce the same binary? | none, you build it |

Dependency advisories, licenses and sources are checked separately by the `security` workflow (`cargo deny`, `cargo audit`). Code signing of the Windows and macOS binaries is built into the release workflow but switched on only by the maintainer's signing secrets; until they are set, releases are unsigned (see [Code signing](#code-signing)).

Status: the SBOM step, the SBOM attestation and the `reproducible` workflow were added together and have not run on GitHub yet; the first tagged release and the first scheduled run are their first real test. If either fails, that is a bug to report, not a sign of tampering.

## Provenance

Every release file carries a signed build provenance. See [Verifying downloads and the image](installation.md#verifying-downloads-and-the-image) for the commands (`gh attestation verify`). `network-scope-<version>.intoto.jsonl` and `.sigstore.json` are the same bundle; for v0.5.1 only, the `.intoto.jsonl` file is instead SLSA level 3 provenance from slsa-github-generator, verified with `slsa-verifier` as described in SECURITY.md. `network-scope-cli update check` and the opt-in desktop setting tell you when a newer release exists and print these commands for it; they never download or replace the program ([Checking for updates](installation.md#checking-for-updates)).

## SBOM

Each release has a [CycloneDX](https://cyclonedx.org/) 1.5 SBOM in JSON, `network-scope-<version>.cdx.json`, generated by `cargo cyclonedx` (version pinned in `release.yml`, installed with `--locked`). It lists the dependency tree of every platform the project ships (Windows, Linux, macOS), with versions, licenses and package URLs, taken from `Cargo.lock`.

The SBOM is a release file like the binaries, so it is listed in `SHA256SUMS` and covered by the provenance attestation. It is also attested as the SBOM of every packaged release file:

```sh
# The SBOM is the signed bill of materials of this file
gh attestation verify network-scope-0.6.0-linux-x86_64.tar.gz \
  --repo Sparkz400/network-scope --predicate-type https://cyclonedx.org/bom

# Offline, with the attestation bundle from the release
gh attestation verify network-scope-0.6.0-linux-x86_64.tar.gz \
  --repo Sparkz400/network-scope --predicate-type https://cyclonedx.org/bom \
  --bundle network-scope-0.6.0.sbom.sigstore.json
```

Then check that the SBOM you read is the attested one (it is a subject of the provenance too):

```sh
gh attestation verify network-scope-0.6.0.cdx.json --repo Sparkz400/network-scope
sha256sum -c --ignore-missing SHA256SUMS
```

Feed it to your own tooling (for example an SBOM scanner such as `grype sbom:network-scope-0.6.0.cdx.json`), or list the components:

```sh
jq -r '.components[] | "\(.name) \(.version)"' network-scope-0.6.0.cdx.json | sort
```

The SBOM describes the Rust dependencies resolved by `Cargo.lock` (including those compiled in from C, such as the bundled SQLite). It does not describe the operating system libraries the binaries load at run time, and the SBOM of the container image is the separate BuildKit attestation stored next to the image.

To generate one yourself:

```sh
cargo install cargo-cyclonedx --version 0.5.10 --locked
cargo cyclonedx --format json --spec-version 1.5 --target all
```

## Reproducible builds

A build is reproducible when the same source gives the same binary, bit for bit, wherever and whenever it is built. Then anyone can rebuild a release and compare the hash, and a binary that differs from the source is detectable without trusting the release workflow.

What is done to get there (`scripts/repro_env.sh`, used by `release.yml` for every platform and by the `reproducible` workflow):

- The toolchain is pinned (`rust-toolchain.toml`), dependencies are locked (`--locked`).
- `SOURCE_DATE_EPOCH` is the commit time of the built commit, so nothing embeds the wall-clock time.
- `--remap-path-prefix` maps the build directory to `/build`, the cargo home to `/cargo` and the rustup home to `/rustup` (and `-ffile-prefix-map` does the same for the bundled C code, on Linux and macOS), so the binary does not contain where it was built.
- `CARGO_INCREMENTAL=0`, and the release profile already uses `lto`, `codegen-units = 1` and `strip`.
- On Windows the paths to remap are given in their long form (`cygpath -w -l`). Windows keeps a short 8.3 name for long folder and user names (`C:\Users\RUNNER~1`, and `TEMP` often holds it); the compiler sees the long name, a prefix in the short form matches nothing, and then the build directory stays inside the binary (2.6 MB of the file differed between two builds before this was fixed).
- `CONST_RANDOM_SEED` is fixed. The `const-random` crate (switched on by `ahash`'s `compile-time-rng`, which `rhai` enables) draws random numbers from the operating system while the compiler runs and builds them into the program, so without a seed every build is different: on Windows some 8,900 bytes of `.text` differed between two builds of one commit, and the `/Brepro` link time and debug GUID, which are hashes of the content, followed. This was the only cause found there. The numbers are the fixed hash keys of the `ahash` maps inside `rhai` and the GUI toolkit; with the seed a release has the same keys in every build (they are public, `ahash` still mixes in an address that ASLR randomizes at run time, and no hash of network data in Network Scope uses them).

### What is reproducible, where

| Platform and file | Status |
| --- | --- |
| Windows x86_64 (MSVC), `network-scope-cli.exe` and `network-scope.exe` | **Measured identical on one machine** (2026-11-20, Windows 11, `sh scripts/repro_check.sh`, commit `2f07242`, `SOURCE_DATE_EPOCH=1795166676`): two exports of the commit in directories of different depth and length, clean `target` folders, both binaries built in each. An earlier manual run of the command-line binary with the seed (directories on two different drives, partly reused `target` folders) gave the same hash for both builds as well. `network-scope-cli.exe`: `4195aeb4f05a2fcd1288b13d49c391e3e4714f6e8006e18e23969b16a0fcc2ac` twice. `network-scope.exe`: `a2c5e1d4d1b94bbe4d87d78e924004c772be3f6905e28c6e8978f6e414267d4b` twice. Not yet measured on a second machine or with another Visual Studio version. |
| Linux x86_64, `network-scope-cli` | The CI job `reproducible build` builds it twice in different directories and compares the hashes; it passes on GitHub (the run on main of 2026-11-21 included). It was not run by hand. |
| macOS, Linux GUI binary, the Windows installer and zip, the container image | Not claimed. Archives and installers contain timestamps; the build flags are the same, nothing else was measured. |

A release built before this change (v0.5.1 and earlier) was built without the seed and **cannot be reproduced**; the first release that carries `CONST_RANDOM_SEED` in `scripts/repro_env.sh` can.

### What CI checks

The `reproducible` workflow runs when `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `src/`, `core/`, `data/`, `assets/` or the scripts change, and every Wednesday. Job `reproducible build` (Linux) exports the commit twice into two directories with different paths, builds `network-scope-cli` in each, and fails if the SHA-256 differs. Job `reproducible build (Windows)` runs `scripts/repro_check.sh`, which does the same for `network-scope-cli.exe` and `network-scope.exe` (clean `target` folders). On a mismatch the binaries are attached to the run for comparison with `diffoscope` or `cmp`. Neither job has run on GitHub yet.

### Check it on your own machine

```sh
sh scripts/repro_check.sh            # Linux, macOS, or Git Bash on Windows; two builds, several minutes each
```

It exports `HEAD` twice, builds both binaries in each copy with the environment of `scripts/repro_env.sh`, prints the hashes and exits with 1 when any differs. On Windows keep the work folder path short (`REPRO_WORK=/c/r`): the linker fails with LNK1104 on paths longer than 260 characters, and cargo's build folder adds about 110. To find out where two files differ, compare them as PE files (the section and the byte ranges); with `/Brepro` the COFF time stamp and the debug GUID are content hashes and differ whenever anything else does, so look at `.text` and `.rdata` first.

### Rebuild a release yourself

For a release built with `CONST_RANDOM_SEED` (see above). On Linux, in the same environment as the release build (the runner image is `ubuntu-latest`; the version is in the log of the `build linux-x86_64` job); a Windows release needs the same Visual Studio build tools as the release job, which are also in its log. A different distribution or linker can change the binary even when everything above matches, so a mismatch there is a question to ask, not yet a proof of tampering.

```sh
git clone https://github.com/Sparkz400/network-scope
cd network-scope
git checkout v0.6.0

# the environment of the release build: SOURCE_DATE_EPOCH, RUSTFLAGS, CFLAGS, ...
env_lines="$(sh scripts/repro_env.sh "$PWD")"
while IFS= read -r line; do export "$line"; done <<< "$env_lines"

cargo build --release --locked --bin network-scope-cli
sha256sum target/release/network-scope-cli

# the same file from the release (compare the binary, not the archive: archives contain timestamps)
tar -xzf network-scope-0.6.0-linux-x86_64.tar.gz
sha256sum network-scope-0.6.0-linux-x86_64/network-scope-cli
```

Equal hashes mean the release binary was built from this source with this toolchain. Run this in `bash` (the `<<<` is not POSIX `sh`). `scripts/repro_env.sh` only prints the variables, so you can read it first.

## Code signing

`release.yml` signs the Windows and macOS binaries when the signing secrets below exist in the repository, and skips signing when they do not: a fork, or this repository before the maintainer has set them up, still publishes a release, unsigned. **No release has been signed yet**; the signing steps have not run.

Signing happens in the jobs `package-windows` and `package-macos`, which take the unsigned binaries from the `build` job, sign them and only then package them. They compile nothing, never run the built binaries and run no package-manager install scripts (Inno Setup is downloaded from its GitHub release and checked against a pinned SHA-256), so the build scripts of the third-party crates never run where the signing credentials or the OIDC token are available. The zip, the installer and the tar.gz contain the signed binaries, and `SHA256SUMS`, the SBOM attestation and the build provenance (all made later, in the `release` job) cover the signed files.

### Windows: SignPath Foundation (free for open source)

[SignPath Foundation](https://signpath.org/) signs open-source projects for free with a certificate issued to the foundation: Windows shows **SignPath Foundation** as the publisher. The project has to apply and be accepted; the conditions include an OSI license, a public repository, automated builds from that repository, multi-factor authentication for the team, and a published [code signing policy](code-signing-policy.md). When `SIGNPATH_API_TOKEN` exists, `package-windows` signs with SignPath and the Azure steps below are skipped:

1. The job uploads the two executables as the artifact `unsigned-windows-executables` (kept one day) and submits it with `signpath/github-action-submit-signing-request` (pinned to its commit), artifact configuration `executables`. SignPath verifies on GitHub that the artifact belongs to this repository's workflow run, waits for the signing request to be approved, signs both files and returns them; they replace the unsigned ones before the zip and the installer are made.
2. After packaging, the installer goes the same way with the artifact configuration `installer`.
3. `Get-AuthenticodeSignature` checks all three files (valid and timestamped), and the `release` job appends SignPath's attribution line, *Free code signing provided by SignPath.io, certificate by SignPath Foundation*, to the release notes.

Setting it up, once SignPath Foundation has accepted the project:

- In SignPath: a project with the slug `network-scope` linked to this GitHub repository as a trusted build system; a signing policy `release-signing` with the foundation's certificate and manual approval; the artifact configurations `executables` and `installer` from [`.signpath/artifact-configurations/`](https://github.com/Sparkz400/network-scope/tree/main/.signpath/artifact-configurations) (both are ZIPs because GitHub artifacts are; each restricts the files to the product name `Network Scope` from their version resources); a CI user with submitter rights on the policy and an API token for it.
- In GitHub, in the `release` environment (limited to `v*` tags):

| Name | Kind | Value |
| --- | --- | --- |
| `SIGNPATH_API_TOKEN` | Secret | API token of the SignPath CI user. **Its presence switches SignPath signing on** (and Azure signing off). |
| `SIGNPATH_ORGANIZATION_ID` | Variable | The SignPath organization ID |
| `SIGNPATH_PROJECT_SLUG` | Variable, optional | Project slug; default `network-scope` |
| `SIGNPATH_SIGNING_POLICY_SLUG` | Variable, optional | Signing policy slug; default `release-signing` |

The job needs `actions: read` so SignPath can read the run and download the artifact with the job's token. Not tried yet: no signing request has been sent, and the artifact configurations have not been loaded into a SignPath project.

### Windows: Azure Artifact Signing

Used when `AZURE_CLIENT_ID` is set and `SIGNPATH_API_TOKEN` is not. `network-scope.exe`, `network-scope-cli.exe` and `NetworkScope-<version>-setup.exe` are signed with [Azure Artifact Signing](https://learn.microsoft.com/azure/artifact-signing/) (formerly Trusted Signing), SHA-256 file digest, RFC 3161 timestamp from `http://timestamp.acs.microsoft.com`. The job checks each signature with `Get-AuthenticodeSignature` (valid and timestamped); the separate job `test-windows`, which holds no credentials, then installs, runs and uninstalls the signed installer (`scripts/installer_smoke.ps1`).

Why Artifact Signing and not `signtool` with a PFX file in a secret: since June 2023 publicly trusted code signing keys must be generated and kept in hardware (CA/Browser Forum baseline requirements), so a new certificate cannot be exported to a PFX file at all. Artifact Signing keeps the key in Microsoft's HSM, costs a monthly fee instead of a yearly certificate, and the workflow logs in with GitHub's OIDC token (a federated credential), so no key or password is stored in GitHub.

Limits:

- Public trust identities are only validated for organizations in some countries and for **individual developers in the United States and Canada** (as of 2026). If the maintainer cannot get an identity, the alternatives are a certificate on a cloud HSM from a CA (DigiCert KeyLocker, SSL.com eSigner, Certum SimplySign) or SignPath Foundation (above), which the workflow already supports.
- The uninstaller inside the installer (`unins000.exe`) stays unsigned: Inno Setup signs it only through its own `SignTool` hook.

Set them as secrets of the `release` environment and limit that environment to `v*` tags (Settings, Environments, Deployment branches and tags), so no other workflow or branch can use them; repository secrets work too.

| Secret | Value |
| --- | --- |
| `AZURE_CLIENT_ID` | Application (client) ID of the Entra ID app registration with a federated credential for this repository, entity type *Environment*, name `release` (the `package-windows` job runs in that environment) and the role *Artifact Signing Certificate Profile Signer* on the signing account. **Its presence switches Azure signing on** (unless `SIGNPATH_API_TOKEN` is set). |
| `AZURE_TENANT_ID` | Directory (tenant) ID |
| `AZURE_SUBSCRIPTION_ID` | Subscription that holds the signing account |
| `ARTIFACT_SIGNING_ENDPOINT` | Endpoint of the signing account's region, for example `https://weu.codesigning.azure.net/` |
| `ARTIFACT_SIGNING_ACCOUNT` | Name of the Artifact Signing account |
| `ARTIFACT_SIGNING_PROFILE` | Name of the certificate profile (Public Trust) |

### macOS: Developer ID and notarization

Both binaries in `network-scope-<version>-macos-arm64.tar.gz` are signed with a Developer ID Application certificate, with the hardened runtime and a secure timestamp, checked with `codesign --verify --strict`, and notarized with `xcrun notarytool` (App Store Connect API key); the job fails unless notarization returns `Accepted`. Notarization takes a zip, so the two binaries are submitted as one and the tar.gz is packed from the same signed files afterwards. A bare command-line binary cannot be stapled (`stapler` works on app bundles, disk images and installer packages only), so macOS fetches the notarization ticket online the first time Gatekeeper checks the binary. The app bundle `Network Scope.app` (built by `packaging/macos/make_app.sh`, released as `network-scope-<version>-macos-arm64-app.zip`) is signed the same way as a bundle (`codesign --verify --strict --deep`), notarized in the same submission and stapled, so it opens without that online check.

| Secret | Value |
| --- | --- |
| `APPLE_CERTIFICATE_P12` | Base64 of the Developer ID Application certificate and its private key, exported as `.p12`. **Its presence switches macOS signing on.** |
| `APPLE_CERTIFICATE_PASSWORD` | Password of that `.p12` file |
| `APPLE_SIGNING_IDENTITY` | The certificate's name, for example `Developer ID Application: Jane Doe (TEAMID1234)` |
| `APPLE_API_KEY_P8` | Base64 of the App Store Connect API key (`AuthKey_<id>.p8`, role Developer) |
| `APPLE_API_KEY_ID` | Key ID of that API key |
| `APPLE_API_ISSUER_ID` | Issuer ID shown on the App Store Connect API keys page |

The certificate is imported into a temporary keychain that the job deletes at the end, and the key files are removed.

Linux binaries and the container image are not code-signed; their proof of origin is the Sigstore provenance above.

### Signatures and reproducible builds

A signature changes the bytes of the file, and only the holder of the key can make it, so a rebuild can never be byte-identical to a signed release binary. The choice made here: **the reproducibility check compares unsigned builds**, and a signed release binary is compared after its signature is removed.

- The `reproducible` workflow and `scripts/repro_check.sh` build twice from source and never sign, so nothing changes for them.
- To compare your rebuild with a signed Windows release binary, remove the signature from the release file, and run the same script on your rebuild (it clears the PE checksum, which signing rewrites):

  ```sh
  python -I scripts/strip_authenticode.py network-scope-cli.exe release-unsigned.exe
  python -I scripts/strip_authenticode.py target/release/network-scope-cli.exe rebuild-unsigned.exe
  ```

  Both commands print the SHA-256 of their output; equal hashes mean the signed binary is the reproducible build plus a signature. The script removes the certificate table, its data directory entry and the checksum, nothing else (checked with `signtool` and a throwaway test certificate on both binaries of a local release build).
- macOS: `codesign --remove-signature` on a copy of the release binary and of your rebuild, then compare. The linker's ad-hoc signature is removed the same way, so both sides end up unsigned. Not tried yet, and macOS builds are not claimed to be reproducible (table above).

`SHA256SUMS` lists the hashes of the signed files, which is what you download.
