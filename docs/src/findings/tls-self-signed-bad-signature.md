# Certificate claims to be self-signed but its signature does not verify

| | |
| --- | --- |
| Finding id | `tls-self-signed-bad-signature` |
| Severity | Medium |
| Applies to | TCP ports that speak TLS |

## What it means

The certificate names itself as its issuer (issuer equals subject), but its signature does not verify with its own public key. A genuine self-signed certificate is signed by the key it contains. This one is not: either another key signed it under the certificate's own name, or the certificate was damaged or altered after it was signed.

## Why it matters

A certificate whose signature is broken is rejected by every TLS client that checks it, so connections either fail or the client has been configured to accept anything. A device that presents such a certificate is misconfigured, was provisioned with a hand-edited file, or something in the network path is substituting certificates.

## How it is detected

The tool treats a certificate as self-issued when issuer and subject are identical and, when both key identifiers are present, the authority key identifier names the certificate's own key. It then verifies the certificate's signature with the certificate's own public key (the `ring` library through the X.509 parser). The result is stored as `tls.<port>.self_signature`: `valid`, `invalid` or `unchecked (reason)`.

The finding is raised only for `invalid`. When the signature is `valid` or `unchecked` the ordinary [self-signed certificate](tls-self-signed.md) finding applies instead. `unchecked` means the verifier cannot make the check, for example for MD5 signatures, RSA keys below 1024 bits (below 2048 bits for SHA-256 and up) or curves other than P-256 and P-384; it is never reported as a problem. The evidence names the certificate subject.

## Possible false positives

- A certificate generated by a tool that writes a wrong signature (rare); the certificate would not work with any verifying client either.
- A certificate that the device re-signed with a different key after export, so that the copy the scanner saw differs from the one the device uses.

## How to fix

- **Replace the certificate** with one that verifies: generate a new key pair and certificate on the device, or issue one from your CA.
- If the certificate was edited by hand, create it again with the tool that normally produces it instead of changing the file.
- If you did not expect this certificate, check for a device in the network path that substitutes certificates.
- **Industrial and embedded devices (OT):** settings like this can often only be changed with the vendor's tools or a firmware update. Follow the vendor's guidance, try the change on a spare unit first, and apply it in an agreed change window with the plant operators informed; a changed setting can interrupt communication with a running process.
- After the change, scan the host again to confirm that the finding is gone.
